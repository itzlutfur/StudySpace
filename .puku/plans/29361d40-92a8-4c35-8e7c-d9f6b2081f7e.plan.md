## Goal

Make the running app match the four reference designs in `reference/` (`Homepage.html`, `course.html`, `player.html`, `settings.html`), which are branded **StudySpace** and styled with **Tailwind**.

Decisions already made with the user:
- **Tailwind** — add as a real dependency and use utility classes in JSX. This reverses the documented decision in `docs/architecture.md` §3 ("Tailwind — rejected: the palette is two token blocks"); that doc must be updated.
- **Full port** — sidebar shell on every page, Dashboard with stat cards, a new **My Courses** page, a redesigned **Player**, and a new **Settings** page.
- **StudySpace branding** — rename the app from CourseStream to StudySpace throughout the UI.

### Tailwind setup

The references use the Tailwind **CDN** (`cdn.tailwindcss.com`). For a built app that is wrong — it ships the whole JIT engine to the browser and flashes unstyled content. Instead install Tailwind as a dev dependency and run it through the existing Vite build:

- `npm i -D tailwindcss @tailwindcss/vite`
- `vite.config.js` → add `tailwindcss()` to `plugins`
- `client/tailwind.config.js` → `content: ['./index.html', './src/**/*.{js,jsx}']`, theme extension for the tokens above
- `client/src/index.css` → `@import 'tailwindcss';` plus `@source` if needed for the Tailwind v4 file-based source detection

Vite's `root: 'client'` means `index.css` lives under `client/src/`. The app entry (`client/src/main.jsx`) must import it.

## Data changes required

The reference screens show data the API does not currently return. These are additive server changes:

1. **Dashboard stats** (`GET /api/dashboard`) — add a `stats` object: `totalCourses`, `totalLessons`, `totalVideos`, `completedLessons`, `totalDurationSec`.
   - Lesson counts come from `listCourses()`; per-course totals need a `durationSec` on lessons.
   - `duration_sec` currently lives on `progress`, not `lessons`. For a *library total* we need the duration of every lesson, including never-played ones. Add a `duration_sec` column to `lessons`, populated during scan/rescan.
2. **Recently Opened list** — the dashboard's "recent lessons" rows need lesson title, course title, type and timestamp. `listCourses()` already exposes `last_opened_at` per course and progress rows carry `last_played`; a small query returns the most recent N lessons across all courses.
3. **Lesson duration** — needed for the Player's "Duration" metadata tile and the playlist's per-lesson time. Same `lessons.duration_sec` column.
4. **Settings page data** — "Library Location" and "Library Status" need the data dir and course count. The data dir is `src/config.js::appDataDir()`; expose it read-only via a new `GET /api/dashboard` field `library: { dataDir, courseCount }` or a dedicated `GET /api/settings`.

Schema migration must be additive and idempotent (`ALTER TABLE lessons ADD COLUMN duration_sec REAL NOT NULL DEFAULT 0` guarded by a column check), because the database lives in `%APPDATA%` and already exists for the user.

### Settings (new page)
- Page header: eyebrow "Preferences / Settings", title "Settings", subtitle "Customize your learning environment."
- **Library & Storage** panel: Library Location (the resolved data dir, shown in a monospace block), Library Status ("Connected" emerald pill).
- **Playback** panel: Default Playback Speed (select 1.0/1.25/1.5/2.0), Resume Playback (toggle), Auto Mark Complete (toggle).
- **Appearance** panel: Theme (select Dark / Light / System), Compact Playlist (toggle).
- **Progress & Data** panel: Export Progress (button), Reset Learning Progress (danger button).
- **About** panel: "About StudySpace" + version pill `1.0.0`.
- Footer: "StudySpace Settings" / "Local-first learning".

**Honesty constraint:** only settings that are actually wired to the backend may appear as interactive controls. The server currently persists only `theme` and `sort` (settings table). Playback speed, resume toggle, auto-complete and compact playlist are **not** implemented — the plan must either (a) implement them server-side as new settings keys, or (b) render them as visibly disabled/"coming soon" rows. To keep this plan honest and bounded, implement (a) for the two that map to real existing behaviour — **Theme** (already persisted) and **Default Playback Speed** (apply `video.playbackRate` on load, persist as a setting) — and render Resume Playback / Auto Mark Complete / Compact Playlist as disabled rows with a "Coming soon" badge. This avoids shipping controls that silently do nothing.

## Server work

| File | Change |
|---|---|
| `src/db/schema.sql` | add `duration_sec REAL NOT NULL DEFAULT 0` to `lessons` |
| `src/db/index.js` | additive, idempotent migration for existing databases (check `PRAGMA table_info`) |
| `src/lib/scanner.js` | capture media duration when it can (best effort; skip on failure) |
| `src/lib/courses.js` | include `durationSec` in the hydrated lesson payload |
| `src/routes/api-dashboard.js` | add `stats` (totalCourses, totalLessons, totalVideos, completedLessons, totalDurationSec), `recent` (recent lessons across courses), `library` (dataDir, courseCount) |
| `src/routes/api-lessons.js` | expose `durationSec` on the lesson and in `grouped` |
| `src/routes/api-courses.js` | expose `durationSec` in `GET /api/courses` and `GET /api/courses/:id` |
| `src/lib/settings.js` | no change needed — the settings table already stores arbitrary keys |
| `src/routes/api-dashboard.js` | extend the existing theme/sort endpoints to accept a generic key/value setter for new settings (playback speed) |

Media duration probing needs a decoder for video files, which the project has no dependency for. **Do not add ffmpeg.** Instead:
- For audio/video, probe duration only when it is cheap and reliable — otherwise leave `duration_sec = 0` and the UI shows "—" for unknown durations.
- A pragmatic approach that works with no new dependency: read the duration from the **progress** rows the user has already watched, and additionally parse duration from MP4/M4A container metadata (`mvhd` atom) for the common case. MP4/MKV duration parsing is a well-bounded task for MP4 (`mvhd`); for MKV it needs EBML parsing — out of scope, so MKV durations show as "—".
- Where duration is unknown, the UI renders "—" instead of a fake number. This is a stated limitation, not a placeholder.

## Risks

- **Tailwind v4 vs v3 config format.** v4 uses CSS-first `@theme` config and the `@tailwindcss/vite` plugin; the `tailwind.config.js` shape differs from v3. Confirm the installed major version and write the config to match it.
- **Class names in JSX must be statically analysable.** No string-built class names (e.g. `bg-${color}-500`) — Tailwind will not generate them. Use a lookup map of full class strings.
- **The `duration_sec` migration** must run on an existing user database without data loss and be idempotent across restarts.
- **Uncommitted working tree.** There are 11 modified files and 2 new files not yet committed. The redesign will touch several of the same files. The plan assumes the redesign builds on the current working tree, not on `HEAD`. The user should commit the existing work first, or accept an overlapping diff.
- **`docs/architecture.md` §3** documents Tailwind as a rejected alternative and will be wrong after this change. Update it.
- **`docs/known-issues.md`** references removed UI elements; update the affected lines.
